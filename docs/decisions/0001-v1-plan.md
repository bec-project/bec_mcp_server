# 0001 — Plan for v1: a read-only diagnostics server

- **Status:** proposed. It replaces most of the v0.1 server on `main`, so it needs the agreement of
  v0.1's author before it is accepted.
- **Date:** 2026-10-08
- **Full plan:** [BEC MCP server: prototype review and rollout plan](https://claude.ai/code/artifact/86faa733-8800-48ec-8da6-c82f2ca9115e)

## Context

`main` holds v0.1: twelve synchronous read-only tools, a qdrant documentation index committed to git,
and streamable HTTP as the default transport. It cannot be installed, because `pyproject.toml`
declares a README that does not exist, and a clean install would fail at startup anyway, because
`BECClient.start()` imports `bec_ipython_client`, which was not a dependency.

A prototype branch, `feat/mcp-extension`, grew v0.1 into a hardened v0.2 and was exercised against a
simulated beamline. It also grew well past diagnostics: about 2,000 of its 5,300 lines serve dev-mode
write tools, GUI control and a source-code knowledge graph. It was validated against `bec_lib` 3.166,
before BEC 4.0 removed the legacy scans and changed the `available_scans` payload.

## Decisions

1. **The server talks to BEC only through one `BECClient`.** It opens no Redis connection of its own.
   In production the agent reaches only the MCP server: it never sees BEC's source code, Redis or the
   file system. Whether reads through the client's own connector with `MessageEndpoints`, for data
   that has no public client accessor, count as going through the client is still open.
2. **The prototype branch is a reference, not a merge source.** It is not merged or pushed. v1 is
   rebuilt from `main` in small pull requests, each copying the code it needs from the branch with
   that code's tests, and each re-tested against BEC 4.
3. **Diagnose first.** v1 is a passive diagnostics server. It registers no tool that can change BEC,
   and it reads cached state only, so no call can queue an RPC or touch hardware. The dev, GUI,
   control and knowledge-graph tiers from the branch stay out of v1, and so does the hand-written
   `llms.md` agent reference, which belongs in `bec_docs`.
4. **Documentation search returns later, rebuilt.** The qdrant index and its tools are removed now.
   They come back as a separate `learn` tier with an in-process BM25 index that is built in
   `bec_docs` CI and loaded by path or URL, instead of an index committed to this repository.
5. **The server stays in its own repository.** It depends only on `bec_lib` from PyPI and needs its
   own release cadence.

## Landing order

| PR | Scope |
| --- | --- |
| 0 | Hygiene: an installable package, CI on Python 3.11 to 3.14 with Black, isort and Pylint, `AGENTS.md`, qdrant removed, this record |
| 1 | Runtime: `mcp` 2.x, stdio by default, HTTP with a bearer token and allowed hosts, worker offload with deadlines, clean shutdown, a per-call audit log, `mcp_status` |
| 2 | Client and status: one `BECClient` with a bounded lifetime, a stdout guard and one module for private `bec_lib` access; `bec_ping`, `bec_status`; a restricted Redis ACL template |
| 3 | Devices: `bec_devices`, `bec_device_info`, `bec_device_read` |
| 4 | Diagnostics: `bec_device_diagnose`, `bec_diagnose` |
| 5 | Queue and beamline states: `bec_queue`, `bec_beamline_states` |
| 6 | Scans: `bec_scans`, `bec_scan_help`, `bec_scan_history` |
| 7 | Logs: `bec_logs` |
| 8 | Docs: the `learn` tier with `bec_docs_search` and `bec_docs_page` |
| 9 | Deployment: the server on the beamline host, the agent in a container |

PRs 3 to 7 depend only on PR 2. PR 4 aggregates 3, 5 and 7, so it lands after them.

## Consequences

- `main` loses its three documentation tools until PR 8.
- PR 0 keeps the v0.1 code on the `mcp` 1.x `FastMCP` API, so it caps `mcp` below 2.0. PR 1 moves
  to the 2.x API and lifts the cap.
- `BECClient` is built for interactive sessions. Its internal structures only grow, some helpers
  print, and the server relies on a few private attributes. PR 2 contains this with a client
  lifetime limit, a stdout guard and a single module for private access.
